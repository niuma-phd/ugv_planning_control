# 实车接口与待办

本文只保留实车联调必须共享的接口、测量项、门禁和后续任务。两科的编译、启动、逐项调试命令以各自操作文档为准。

## 1. 系统边界

### 1.1 共同约束

- 当前实车是两侧差速履带底盘。
- 两个科目分别运行，不能同时启动；各自运行图中只能有一个最终 `/cmd_vel` 发布者。
- 最终车控接口固定为 `/cmd_vel`、`geometry_msgs/msg/Twist`：
  - `linear.x`：前进速度，单位 m/s，正值向前；
  - `angular.z`：偏航角速度，单位 rad/s，正值左转；
  - 其余四个分量必须为 0。
- 本仓库不输出履带转速、PWM、油门、转角或 CAN 帧。左右履带换算、符号适配、急停和独立命令超时看门狗由下游车控团队负责。
- `Twist` 没有时间戳和失效时间。即使本仓库会在输入异常时归零，下游也必须独立实施看门狗，不能依赖 ROS 发布端作为唯一安全措施。
- 雷达驱动和 LIO 是只读外部依赖，本仓库不修改、不复制它们的源码。

### 1.2 科目二：自主导航接口

| 方向 | 话题 | 类型 | 责任与要求 |
|---|---|---|---|
| 输入 | `/livox/lidar` | `sensor_msgs/msg/PointCloud2` | Horizon 驱动发布；LIO 必须使用 `ScanRegistration.msg_type=1` |
| 输入 | `/livox/imu` | `sensor_msgs/msg/Imu` | Horizon 驱动发布；量纲和重力缩放必须经过实测确认 |
| 输入 | `/livox_odometry_mapped` | `nav_msgs/msg/Odometry` | 外部 LIO 发布的原始雷达位姿 |
| 输入 | `/subject2/path` | `nav_msgs/msg/Path` | 按顺序排列的全局路径，`header.frame_id=map`；上游真实进程、传输和刷新规则尚未确认 |
| 内部标准化 | `/localization/odom` | `nav_msgs/msg/Odometry` | `lio_odom_adapter` 输出，`odom→base_link` |
| 内部安全输入 | `/localization/trusted_odom` | `nav_msgs/msg/Odometry` | 通过连续性与时效检查后供控制器使用 |
| 内部状态 | `/localization/odom_valid` | `std_msgs/msg/Bool` | 定位有效门禁 |
| 证据 | `/localization/last_trusted_odom` | `nav_msgs/msg/Odometry` | 故障前最后可信样本，用于恢复和排障 |
| 输出 | `/cmd_vel` | `geometry_msgs/msg/Twist` | Pure Pursuit 最终平面速度命令 |

标准化里程计必须使用 `header.frame_id=odom`、`child_frame_id=base_link`，时间戳非零且严格递增。路径、TF、可信里程计或有效状态缺失、超时、跳变或不合法时，控制器输出零命令。

`/subject2/path` 只是本仓库内部控制器的标准输入，不代表合作方会直接发布 ROS 2 话题。合作方接口确认后再实现独立适配器，不把上游解析逻辑塞进控制器。

### 1.3 科目一：局部避障接口

| 方向 | 话题 | 类型 | 责任与要求 |
|---|---|---|---|
| 输入 | `/livox/lidar` | `sensor_msgs/msg/PointCloud2` | Horizon 点云，转换到 `base_link` 后做障碍物栅格提取 |
| 合作方输入 | `/subject1/next_waypoint_base` | `geometry_msgs/msg/PointStamped` | 下一航点已经转换到 `base_link`；时间戳非零、严格递增且坐标系必须正确 |
| 合作方输入 | `/subject1/nominal_cmd_vel` | `geometry_msgs/msg/Twist` | 无障碍时的持续巡航命令；只允许有限的 `linear.x`、`angular.z` 和其余分量为 0 |
| 内部感知 | `/subject1/obstacles` | `geometry_msgs/msg/PoseArray` | `base_link` 下的占用栅格中心 |
| 输出 | `/cmd_vel` | `geometry_msgs/msg/Twist` | 巡航/避障原子选择后的唯一最终命令 |
| 诊断 | `/subject1/avoidance_active` | `std_msgs/msg/Bool` | 避障或故障停车分支是否生效 |
| 诊断 | `/subject1/avoid_cmd_vel` | `geometry_msgs/msg/TwistStamped` | 局部避障候选命令 |
| 诊断 | `/subject1/selected_trajectory` | `nav_msgs/msg/Path` | 选中的机体系 rollout 轨迹 |

选择规则为 fail-closed：无相关障碍且巡航命令新鲜合法时透传巡航命令；存在障碍且有安全局部轨迹时输出避障命令；全部轨迹受阻，或感知、航点、被选命令出现缺失、超时、错误坐标系、非有限值、非平面分量时输出零。时间戳为零、重复或倒退的障碍物/航点样本会被丢弃且不刷新接收时刻；上一有效输入最多保留到 `input_timeout_s`（当前 `0.30 s`），随后归零。不能因局部输入异常而回退到巡航命令。

科目一的局部闭环不依赖全局对齐即可工作，但合作方必须直接提供 `base_link` 下的下一航点。当前 Horizon 包装器仍会启动 LIO 和定位节点，用于后续 TF/定位集成；局部避障控制本身不读取 LIO 里程计。

### 1.4 全局对齐与恢复入口

| 接口 | 类型 | 当前规则 |
|---|---|---|
| `/localization/map_odom_update` | `geometry_msgs/msg/TransformStamped` | 人工或未来恢复管理器提供审核后的 `map→odom` 更新 |
| `/localization/reset_odom_fault` | `std_srvs/srv/Trigger` | 明确复位里程计故障；不能把自动重启当作已实现能力 |

科目二暂时发布恒等 `map→odom`，只表示封闭场地内“物理起点与路径起点一致”的临时假设，不证明未知上游地图的原点、坐标轴或航向已经对齐。科目一以 `initial_transform_valid=false` 启动，在收到显式审核更新之前不发布 `map→odom`。

## 2. TF 与实测回填

### 2.1 TF 权责

当前目标 TF 链为：

```text
map → odom → base_link → livox_frame
```

- `base_link→livox_frame`：本团队负责测量并发布静态 TF；Horizon 六自由度外参未审核时必须保持关闭。
- `odom→base_link`：`lio_odom_adapter` 根据 LIO 雷达位姿与静态外参计算并发布：

  ```text
  T_odom_base = T_raw_world_lidar × inverse(T_base_lidar)
  ```

- LIO 原始 `world→livox_frame` TF 被重映射到 `/lio_raw/tf`，不得与规范车辆 TF 树争夺父子关系。
- `map→odom`：由本仓库的 `map_odom_manager` 发布；科目二当前使用临时恒等变换，科目一等待显式更新。
- 其他传感器静态 TF 由对应团队测量。本团队只提出坐标、精度、记录和审核要求。

### 2.2 雷达外参记录

每次测量必须形成可追溯记录，而不是只把数值写入启动命令：

- 父坐标系 `base_link`、子坐标系 `livox_frame` 的物理定义；
- 平移 `x/y/z`，单位 m；固定轴姿态 `roll/pitch/yaw`，单位 rad；
- 各轴测量不确定度、测量工具、日期、车辆载荷和安装状态；
- 测量记录编号 `lidar_extrinsics_provenance`、复核人和批准结论；
- 静止点云地面高度、车体轴向和已知目标位置的复验结果。

启动时只有同时提供六个有限数值、非空记录编号并设置 `publish_lidar_static_tf:=true`，规范里程计和静态 TF 才会启用。默认零值不是可用外参。

### 2.3 车辆与感知参数实测项

| 类别 | 必须回填/验证的项目 | 影响参数或门禁 |
|---|---|---|
| 外形 | 含固定突出物的最大长、宽、高、最低离地间隙；能否采用矩形 footprint；否则给出 `base_link` 下逆时针多边形顶点 | 科目一 footprint、自车裁剪和膨胀区 |
| 坐标基准 | `base_link` 物理位置；相对车头、左缘、地面的尺寸；规划/控制参考点相对 `base_link` 的 `x/y/z` | TF、路径跟踪误差和停车位置 |
| 底盘运动 | 两侧履带正负号、能否倒车、能否原地转向 | 下游适配与测试用例 |
| 运动限制 | 最大允许/首次联调前进速度、稳定偏航角速度、最大曲率、最小转弯半径、最大线加/减速度、最大偏航角加速度 | `subject1.yaml`、`subject2.yaml` 与下游限幅 |
| 停车安全 | 命令归零至开始减速的 95/99 分位延迟；指定低速下最大停车距离 | 看门狗、超时阈值、安全区和首次联调门禁 |
| 点云区域 | 车体自遮挡边界、前向/横向 ROI、障碍高度带、栅格尺寸、最低点数 | `roi_*`、`self_*`、`min_z/max_z`、`cell_size`、`min_points` |
| 避障余量 | 车体半长/半宽、膨胀距离、走廊宽度、规划视距 | `footprint_*`、`inflation_m`、`corridor_*`、`horizon_m` |
| 定位统计 | 静止漂移、正常运动增量、时间戳延迟、位置/航向跳变分布 | `odom_guard` 超时和跳变阈值 |

当前 YAML 中的 footprint、ROI、高度带、速度、曲率、跳变阈值均为候选值，不能当作实车标定结果。

## 3. 启动前门禁

### 3.1 两科共同门禁

- 驱动、LIO 和本仓库均固定到已审核提交，RDK 终端按正确 overlay 顺序加载。
- 使用经过验证的 Horizon broadcast-code 白名单；生产运行不得依赖自动发现。
- `base_link→livox_frame` 六自由度、误差和记录编号已经审核。
- `/livox/lidar` 类型确认为 `PointCloud2`，LIO 参数确认为 `msg_type=1`，IMU 量纲和重力缩放冲突已用静止与运动数据解决。
- 原始 LIO TF 只出现在 `/lio_raw/tf`，规范 TF 每一条边只有一个发布权威。
- 下游已确认履带符号、限幅、独立 `/cmd_vel` 看门狗、现场急停和遥控停车。
- 首次验证保持执行器断开；所有失效注入都能在要求时间内产生零命令后，才能进入低速联调。
- 一次只运行一个科目，并确认 `/cmd_vel` 恰好一个发布者。

### 3.2 科目二附加门禁

- 使用真实 Horizon 点云验证 PointCloud2 对应的 LIO `FeatureExtract_Mid` 路径，不能沿用 CustomMsg 的调参结论。
- 路径已经人工复核，并且原点和坐标轴有意满足当前恒等 `map→odom` 假设。
- 路径刷新、LIO/odom 断流、时间戳异常、位姿跳变和 TF 缺失均已在断开执行器时验证为零命令。
- 先完成直线，再做左/右弧线，最后验证终点停车和制动距离；任一 TF、定位或命令行为无法解释时停止联调。

### 3.3 科目一附加门禁

- 真实点云已验证 `base_link` 轴向、地面高度、车体裁剪、障碍高度带、ROI 和安全膨胀。
- 合作方持续提供新鲜的 `/subject1/nominal_cmd_vel` 和 `base_link` 下的 `/subject1/next_waypoint_base`。
- 已在断开执行器条件下覆盖：无障碍透传、检测障碍接管、障碍解除回切、全部受阻停车，以及 stale/wrong-frame/replay/non-finite/non-planar 停车。
- 未获得审核后的 `map→odom` 时，不把任何未知地图航点直接用于科目一；局部输入仍须由合作方转换到 `base_link`。

## 4. 当前已知限制

- 上游路径和全局位姿的真实进程、传输、坐标基准、时间同步、质量字段和重启行为尚未确定，当前没有生产适配器。
- 自动 GPS/全局位姿辅助恢复尚未实现。里程计故障后的正确行为是停车并保存最后可信样本；LIO 重启接口、重启后首个有效样本规则和安全 `map→odom` 更新流程仍待确认。
- 科目二恒等 `map→odom` 只适用于已人工对齐的封闭路径。
- 科目一感知采用确定性二维栅格，避障采用常曲率 rollout；尚不处理动态障碍、负障碍或高级地形分割。
- 当前闭环与实车验证目标是 Horizon；Avia 不属于本轮已验证启动链。
- 本仓库不实现底盘执行器协议或下游硬件看门狗。

## 5. 后续优先级

### P0：先闭环科目二

1. 完成 Horizon 外参、IMU 重力缩放和 PointCloud2 LIO 实测。
2. 在执行器断开状态完成 TF 单权威、路径/定位故障归零和停车证据。
3. 审核履带符号、车辆限幅、独立看门狗、急停和首测速度。
4. 使用与恒等 `map→odom` 对齐的封闭路径完成低速直线、左右弧线和终点停车。

### P0：科目一达到可上车门槛

1. 回填 footprint、自车裁剪、ROI、高度带、膨胀和速度/曲率参数。
2. 接入合作方持续巡航命令和 `base_link` 航点。
3. 在执行器断开状态完成巡航/避障切换及全部 fail-closed 用例。
4. 确认唯一 `/cmd_vel` 发布者和下游独立看门狗后，再低速联调。

### P1：确认接口后再做

1. 根据合作方实际形式实现独立的路径/全局位姿适配器。
2. 定义全局坐标基准、质量门限和时钟关系，替换临时恒等 `map→odom`。
3. 明确 LIO supervisor/restart 边界、重启后有效判据和车辆停止期间的原子对齐流程，再实现 GPS 辅助恢复。
4. 只有真实场地证明固定高度栅格不足时，才评估更复杂的聚类或地形分割。

## 7. 开源算法参考

当前 MVP 只独立实现小型算法，不在运行时链接 Nav2、Autoware、PythonRobotics 或 PCL。

- 科目二 Pure Pursuit：
  - [Nav2 Humble Regulated Pure Pursuit（Apache-2.0）](https://github.com/ros-navigation/navigation2/tree/humble/nav2_regulated_pure_pursuit_controller)
  - [PythonRobotics Pure Pursuit（MIT）](https://github.com/AtsushiSakai/PythonRobotics/tree/master/PathTracking/pure_pursuit)
  - 当前核心关系：`curvature = 2 * target_y_in_base / lookahead_distance²`，`omega = speed * curvature`。
- 科目一感知：
  - [Autoware Euclidean Cluster（Apache-2.0）](https://autowarefoundation.github.io/autoware_universe/main/perception/autoware_euclidean_cluster/)
  - [PCL 滤波/体素/聚类概念（BSD-3-Clause）](https://pointclouds.org/)
  - 当前实现使用 `PointCloud2Iterator` 和二维栅格，避免引入大型 PCL 开发依赖。
- 科目一避障：
  - [Nav2 DWB（Apache-2.0）](https://github.com/ros-navigation/navigation2/tree/humble/nav2_dwb_controller)
  - [PythonRobotics Dynamic Window Approach（MIT）](https://github.com/AtsushiSakai/PythonRobotics/tree/master/PathPlanning/DynamicWindowApproach)
  - 当前实现采样常曲率轨迹，不引入完整插件和 costmap 框架。
- 备选地形分割：[Patchwork++](https://github.com/url-kaist/patchwork-plusplus)。其仓库核心代码与 ROS 包元数据存在 BSD-2-Clause/GPL-3.0 混合许可信号；未经逐文件许可审查，不复制或 vendor 其 ROS wrapper。
