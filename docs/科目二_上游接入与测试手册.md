# 科目二上游接入与测试手册

本文面向路径数据合作方、路径适配器开发者和现场联调人员，说明如何把上游数据接入科目二控制器，以及如何在**执行机构断开**时完成验收。

科目二总体启动、定位链路和控制参数见[科目二自主导航使用说明](科目二_自主导航使用说明.md)；尚未闭合的坐标、车辆和恢复问题见[实车接口与待办](实车接口与待办.md)。

> **本轮验证边界**：RDK 当前离线，本轮没有在 RDK 或实车上执行本文命令，也不把任何 RDK/实车测试记为通过。仓库自带 fixture 使用隔离的 `/fixture/*` 话题，只能验证软件行为，不能替代实车放行。

## 1. 先明确责任边界

合作方**不需要编写 ROS 2 程序**。接入链路分为三层：

```text
合作方原始数据
  → 待确认的独立适配器
  → /subject2/path（nav_msgs/msg/Path）
  → 本仓库 waypoint_controller_node
  → /cmd_vel
```

| 层级 | 责任方 | 交付内容 |
|---|---|---|
| 合作方原始数据 | 合作方 | 能稳定输出路径点及其时间、坐标和有效状态的现有程序；说明真实接口 |
| 路径适配器 | 本团队，接口确认后实现 | 解析真实数据、校验状态、换算单位和坐标、生成标准 ROS `Path` |
| 跟踪控制器 | 本仓库 | 校验标准 `Path`，结合可信里程计计算 `/cmd_vel` |

当前仓库**没有生产路径适配器**。不要要求合作方照本文直接发布 ROS，也不要在真实接口确认前猜测 TCP、UDP、串口、文件或 JSON 协议。

## 2. `/subject2/path` 的硬契约

控制器订阅：

```text
话题：/subject2/path
类型：nav_msgs/msg/Path
QoS：reliable / volatile / depth 1
```

| 项目 | 硬性要求 | 不满足时的行为 |
|---|---|---|
| `header.frame_id` | 必须精确等于 `map` | 当前路径被清除，下一控制周期输出零命令 |
| `header.stamp` | 必须是合法 ROS 2 时间：`sec>=0`、`nanosec<1e9`、总值大于零，且在本次控制器进程生命周期内严格递增 | 当前路径被清除；非法、重复或倒退时间戳均拒绝 |
| `poses` | 至少 1 点且不能为空 | 当前路径被清除 |
| 每点 `header.frame_id` | 空字符串或 `map` | 当前路径被清除 |
| 每点 `pose.position.x/y` | 有限数，单位 m | 当前路径被清除 |
| `position.z` | 控制器不读取 | 不参与校验、跟踪或几何变更判断 |
| 姿态、每点时间戳 | 控制器不读取 | 不参与跟踪或几何变更判断 |
| 刷新周期 | 接收间隔不得超过 5.0 s | 超时后的下一次 20 Hz 控制周期输出零命令 |

推荐的上游质量要求：

- 至少提供 2 个有序点；单点只满足消息合法性，通常无法形成有意义的跟踪路径。
- 按车辆应行驶的先后顺序排列路径点，不要把无序点集当作路径。
- 相邻点间距建议 `0.2～0.5 m`，当前 fixture 使用 `0.25 m`。
- 建议以 `1 Hz` 刷新，给 `5.0 s` 硬超时保留抖动余量。
- 当前临时假定 `map` 与 `odom` 重合。路径原点、X/Y 轴方向和初始航向必须人工确认与车辆定位一致。
- 路径应从车辆附近开始并向前延伸；路径整体位于车后、点序反向或几何自交可能导致停车或错误选点。

### 2.1 刷新与进度重置规则

控制器区分“刷新同一条路径”和“换了一条路径”：

- 仅 `header.stamp` 更新，且顶层/每点 frame、点数、每点 `x/y` 都与上一条被接受路径完全相同：刷新 5 秒超时，**不重置**路径跟踪进度。
- 顶层或每点 frame、点数、任一点 `x/y` 改变：接受新路径，同时**重置**跟踪进度。
- `z`、姿态或每点时间戳改变：当前实现不视为几何变化。

比较 `x/y` 时使用精确值。适配器周期刷新同一路径时，应复用稳定的坐标值，避免无意义的浮点抖动导致每秒重置进度；真正重规划后则应发布新几何。

`header.stamp` 的严格递增范围是当前控制器进程生命周期。适配器重启后若时间戳回退，控制器会持续拒绝，直到新时间戳超过最后一次已接受值，或控制器也被重启。

### 2.2 不得用“心跳”掩盖原始数据断流

适配器可以用新时间戳刷新同一几何，但前提是它仍能确认原始数据源健康、该路径仍有效。原始接口断流或报告路径失效后，适配器不得无限给缓存路径换时间戳，否则控制器的 5 秒超时永远不会触发。

当前标准接口没有单独的“路径有效”话题。适配器停止发布后，控制器最迟在 `path_timeout_sec=5.0 s` 后停车；若业务要求更快的上游失效响应，需要另行确认接口和时延指标，不能把它写成当前已实现能力。

### 3.2 GPS 恢复输入确认表

真实 GPS 提供方同样**不需要编写 ROS 2 节点**，但必须说明原始接口，使本团队能适配出 `/localization/gps_pose` (`geometry_msgs/msg/PoseWithCovarianceStamped`)：它必须是 `map` 下 `base_link` 的 x/y/z/yaw，并另行发布质量心跳 `/localization/gps_valid`。协方差 36 项全部必须是有限数；索引 `[0,7,14,35]` 分别是 x/y/z/yaw 方差，均必须严格大于 0，当前候选上限分别为位置 `4.0 m²` 和 yaw `0.25 rad²`。

| 必须确认的信息 | GPS 提供方/测量负责人填写 |
|---|---|
| 设备、解算程序、版本和负责人 |  |
| 原始接口、完整样例、刷新频率和断流表达 |  |
| datum/坐标原点、投影方法、X/Y/Z 轴向和单位 |  |
| 时间戳来源、单位、同步误差和回退规则 |  |
| yaw 的真实观测来源、正方向、单位和可信条件 |  |
| x/y/z/yaw 协方差或可转换的质量指标 |  |
| fix 类型、星数、RTK 状态、无效/降级如何表示 |  |
| GPS 天线相对 `base_link` 的 x/y/z 外参及测量记录 |  |
| 静止/低速时能否稳定提供 yaw；无法提供时如何标无效 |  |

仓库中真实 GPS 适配器尚未实现，必须等真实接口确认后开发和验收。外部 LIO 发布的 `/lidar` (`sensor_msgs/msg/NavSatFix`) 只是用 latitude/longitude/altitude 字段包装 LIO 伪坐标，**不是真实 GPS，禁止适配为恢复输入**。雷达点云、LIO odom 和合成 fixture 也不能当作实车 GPS 验收依据。

## 4. 标准 ROS `Path` 字段样例

下例展示适配器应产生的消息结构。数值时间戳只是格式示例，不能在周期发布时重复使用：

```yaml
header:
  stamp:
    sec: 1784970000
    nanosec: 125000000
  frame_id: map
poses:
  - header:
      stamp: {sec: 1784970000, nanosec: 125000000}
      frame_id: map
    pose:
      position: {x: 0.0, y: 0.0, z: 0.0}
      orientation: {x: 0.0, y: 0.0, z: 0.0, w: 1.0}
  - header:
      stamp: {sec: 1784970000, nanosec: 125000000}
      frame_id: map
    pose:
      position: {x: 0.25, y: 0.0, z: 0.0}
      orientation: {x: 0.0, y: 0.0, z: 0.0, w: 1.0}
  - header:
      stamp: {sec: 1784970000, nanosec: 125000000}
      frame_id: map
    pose:
      position: {x: 0.50, y: 0.02, z: 0.0}
      orientation: {x: 0.0, y: 0.0, z: 0.0, w: 1.0}
```

建议适配器使用发布时 ROS 时钟填写顶层 `header.stamp`，并保证严格递增。每点 frame 可为空，但统一填 `map` 更便于排查。控制器只使用每点 `x/y`；仍建议把未使用的 `z` 设为 `0`、姿态设为单位四元数，避免其他工具误读垃圾值。

不要用固定时间戳的 `ros2 topic pub --rate ...` 模拟长期上游：第二条消息开始就会因时间戳重复而被拒绝。周期测试应使用仓库 fixture 或真正会更新时间戳的适配器。

## 5. QoS 兼容要求

控制器请求 `reliable / volatile / depth 1`。

| 发布端配置 | 是否可接入 | 说明 |
|---|---|---|
| `reliable / volatile / depth 1` | 是，生产推荐 | 与控制器完全一致 |
| `reliable / transient_local` | DDS 可兼容 | 本仓库 fixture 使用；生产仍推荐 volatile，避免依赖历史缓存语义 |
| `best_effort` | 否 | 不能满足 reliable 订阅，控制器可能完全收不到路径 |
| 深度大于 1 | 通常可通信 | 不改变契约；控制器只保留最近被接受的路径 |

适配器启动后检查实际端点：

```bash
ros2 topic info -v /subject2/path
```

在输出的 Publisher endpoint 中确认：

- Topic type 为 `nav_msgs/msg/Path`；
- Reliability 为 `RELIABLE`；
- Durability 推荐 `VOLATILE`；
- 生产图中只有预期的路径发布者。

## 6. 上游自检

以下检查先只启动合作方程序和适配器，不连接执行机构：

```bash
ros2 topic type /subject2/path
ros2 topic info -v /subject2/path
ros2 topic echo /subject2/path --once
ros2 topic hz /subject2/path
```

验收：

1. 类型精确为 `nav_msgs/msg/Path`，发布端为 reliable。
2. `header.frame_id` 为 `map`；顶层时间戳满足 `sec>=0`、`nanosec<1e9` 且总值大于零。
3. 连续观察多条消息，顶层时间戳每次严格增加。
4. `poses` 非空；每点 frame 为空或 `map`；所有 `x/y` 都是有限的米制坐标。
5. 路径点顺序与预期行驶方向一致，相邻点建议 `0.2～0.5 m`。
6. `ros2 topic hz` 稳定在双方约定值，建议约 `1 Hz`，任何间隔都不能达到 5 秒。
7. 保持路径几何不变刷新时，`x/y` 不应出现无意义末位抖动。

再启动控制器但仍断开执行机构，观察：

```bash
ros2 topic echo /subject2/target_point
ros2 topic echo /cmd_vel
ros2 topic info -v /cmd_vel
```

只有路径、可信里程计、有效状态和 TF 同时成立时才应出现非零命令。`/cmd_vel` 必须恰好有一个发布者。

## 7. CSV 航点文件测试

这是不依赖真实上游的显式开发功能，不在生产 launch 中默认启动。它位于 `ugv_mvp_tools`，必须先构建完整开发工作区：

```bash
cd /path/to/ugv_planning_control
source /opt/ros/humble/setup.bash
colcon build --cmake-args -DCMAKE_BUILD_TYPE=Release
source install/setup.bash
```

复制安装示例并编辑：

```bash
EXAMPLE="$(ros2 pkg prefix ugv_mvp_tools)/share/ugv_mvp_tools/config/example_waypoints.csv"
cp "$EXAMPLE" "$HOME/subject2_waypoints.csv"
${EDITOR:-nano} "$HOME/subject2_waypoints.csv"
```

CSV 必须含 `x_m,y_m`，可选 `z_m,yaw_rad`，至少 2 点且有一段非重合路径。禁止额外/重复列、空值、NaN/Inf 和多余字段。任一行无效时节点在创建 publisher 前拒绝整个文件，不发布部分路径。

启动与观察：

```bash
ros2 run ugv_mvp_tools waypoint_file_publisher_node --ros-args \
  -p path_file:="$HOME/subject2_waypoints.csv" \
  -p topic:=/subject2/path -p frame_id:=map -p rate_hz:=1.0

# 另开终端
ros2 topic hz /subject2/path
ros2 topic echo /subject2/path --once
ros2 topic echo /cmd_vel
```

发布器以 1 Hz 刷新标准 `/subject2/path`，每次使用严格递增时间戳。修改文件后需重启节点重读；在发布器终端按 `Ctrl+C` 停止。完整字段规则和命令见[科目二自主导航使用说明](科目二_自主导航使用说明.md)。

## 8. 分层测试流程（始终先断开执行机构）

### 第 1 层：原始接口

- 录制正常直线、左弯、右弯和路径更新样例。
- 录制断流、无效状态、空结果、重连和进程重启样例。
- 核对第 3 节确认表，不接 ROS 控制器。

通过标准：原始数据字段、时钟、坐标、状态和重启行为均可解释并可重复回放。

### 第 2 层：适配器输出

只运行适配器，用第 6 节命令检查类型、QoS、frame、时间戳、点序、间距和刷新。主动停止原始数据源，确认适配器不会继续给缓存路径伪造新鲜时间戳。

通过标准：标准 `Path` 满足第 2 节全部硬契约；断流行为与记录一致。

### 第 3 层：仓库隔离 fixture

fixture 使用合成路径、里程计和恢复输入，所有生产话题都重映射到 `/fixture/*`。它验证控制、门禁、恢复顺序和停车行为，**不验证合作方适配器、真实 GPS、雷达、真实 LIO/RDK 进程、外参、底盘或实车**。

先单独构建并测试三个科目二生产包：

```bash
source /opt/ros/humble/setup.bash
bash scripts/build_subject2.sh --clean
colcon --log-base log_subject2 test \
  --build-base build_subject2 \
  --install-base install_subject2 \
  --packages-select \
    ugv_localization_mvp \
    ugv_subject2_mvp \
    ugv_subject2_bringup \
  --event-handlers console_cohesion+
colcon test-result --test-result-base build_subject2 --verbose
```

最后一条命令必须显示 `0 errors`、`0 failures`、`0 skipped`。不要把测试数量写进自动化判定，
因为后续增加回归用例时数量会变化。这里的 `--install-base install_subject2` 不能省略，否则
`colcon test` 会错误地查找默认 `install/`。

先完成完整开发构建（科目二生产脚本不包含 `ugv_mvp_tools`）：

```bash
source /opt/ros/humble/setup.bash
colcon build --cmake-args -DCMAKE_BUILD_TYPE=Release
source install/setup.bash
```

| 模式 | 注入内容 | 自动验收重点 |
|---|---|---|
| `subject2` | 左弯路径 | 有正线速度、正角速度和 `map` 下目标点 |
| `subject2_right` | 右弯路径 | 有正线速度、负角速度 |
| `subject2_line` | 直线路径 | 有正线速度、角速度接近零 |
| `subject2_path_timeout` | 3 秒后停止路径发布 | 先行驶，路径接收超时后归零 |
| `subject2_path_replay` | 3 秒后重复同一时间戳 | 先行驶，重复时间戳被拒绝后归零 |
| `subject2_path_wrong_frame` | 路径 frame 为 `unknown_map` | 始终不产生正速度 |
| `subject2_path_zero_stamp` | 路径顶层时间戳为零 | 始终不产生正速度 |
| `subject2_path_negative_stamp` | 路径时间戳 `sec=-1` | 控制节点保持存活且始终不产生正速度 |
| `subject2_path_invalid_nanosec` | 路径时间戳 `nanosec=1e9` | 控制节点保持存活且始终不产生正速度 |
| `subject2_path_empty` | `poses` 为空 | 拒绝日志出现，控制节点保持存活且始终不产生正速度 |
| `subject2_path_wrong_pose_frame` | 每点 frame 为 `unknown_map` | 拒绝日志出现，控制节点保持存活且始终不产生正速度 |
| `subject2_path_nonfinite` | 首点 `x=NaN` | 拒绝日志出现，控制节点保持存活且始终不产生正速度 |
| `subject2_odom_timeout` | 6 秒后停止原始里程计 | 有效状态转 false、归零、快照内容一致 |
| `subject2_odom_jump` | 6 秒后注入 5 m 跳变 | 锁存平移跳变、归零、快照内容一致 |
| `subject2_odom_invalid_stamp` | 6 秒后向保护器直发 `sec=-1` 的规范 odom | 锁存 `invalid_stamp`、保存最后可信值、归零且节点保持存活 |
| `subject2_waypoint_file` | 用临时严格 CSV 代替合成路径节点 | 文件完整加载，路径刷新，产生正线速和左转角速度 |
| `subject2_recovery_success` | odom 失效，合成 GPS 有效，重启服务成功且新 odom 改变原点 | 严格按 `WAIT_GPS→WAIT_LIO→RUNNING` 恢复，更新/回显 `map→odom`；恢复完成前全程零速 |
| `subject2_recovery_no_gps` | odom 失效但始终无合格 GPS | 超时进入 `ABORTED`，从故障到测试结束始终零速 |
| `subject2_recovery_restart_failed` | GPS 有效但 `/localization/restart_lio` 返回失败 | 立即进入 `ABORTED`，故障期始终零速 |

脚本成功时输出 `SUBJECT2_FIXTURE_SMOKE_OK`。fixture 中的零外参带有 `fixture-zero-do-not-use-on-vehicle` 标记，禁止复制到实车启动命令。

成功恢复的验收顺序必须是：里程计锁存失效并禁止导航 → 故障前最后可信 odom 和当前 `map→odom` 可用 → 故障后新 GPS 连续稳定 → 已有新鲜 `/localization/lio_generation` 旧代基线 → 受管 LIO 进程组重启 → generation 变化且 `/localization/lio_process_alive=true` 持续新鲜 → 丢弃不晚于重启服务完成时刻的旧代排队 odom → 再次获得新 GPS 和重启后新 odom 稳定窗口 → 更新 `map→odom` → 管理器回显一致 → 复位 odom guard → 新可信 odom 与 GPS 最终一致 → 恢复 `RUNNING`。“重启服务 success”不是恢复成功。任一失败或超时进入 `ABORTED`，默认最多 1 次尝试，且故障期到验证完成前始终零速。

### 第 4 层：适配器与真实控制图联调

保持底盘驱动器、CAN 输出或执行器使能断开，启动真实适配器、定位链和科目二控制器：

1. 先发直线路径，再发左右弯路径，核对 `/subject2/target_point` 和 `/cmd_vel` 符号。
2. 同几何持续刷新，确认控制目标不会反复退回路径起点。
3. 发布有意义的新几何，确认进度重置后目标点符合新路径。
4. 依次执行第 9 节故障注入，并确认 `/cmd_vel` 归零。
5. 保存终端日志、上游原始数据、标准 `Path` 和 `/cmd_vel` 记录。

只有本层全部通过、车辆限速/制动/急停/下游独立看门狗均审核后，才能另行批准低速实车测试。本轮未进行该批准或测试。

## 9. 故障矩阵

| 故障/操作 | 当前控制器预期 | 检查方法或 fixture |
|---|---|---|
| 无 `/subject2/path` 发布者 | 保持零命令 | `ros2 topic info -v` |
| 发布类型不是 `nav_msgs/msg/Path` | 无法连接，保持零命令 | `ros2 topic type` |
| 发布端仅 best effort | QoS 不兼容，最终按无路径处理 | `ros2 topic info -v` |
| `poses` 为空 | 立即拒绝当前路径并归零 | `subject2_path_empty` |
| 顶层 frame 不是 `map` | 立即拒绝并归零 | `subject2_path_wrong_frame` |
| 顶层时间戳为零 | 立即拒绝并归零 | `subject2_path_zero_stamp` |
| 顶层时间戳秒数为负 | 立即拒绝并归零，控制节点不得退出 | `subject2_path_negative_stamp` |
| 顶层时间戳纳秒数不小于 `1e9` | 立即拒绝并归零，控制节点不得把它自动进位后接受 | `subject2_path_invalid_nanosec` |
| 顶层时间戳重复或倒退 | 立即拒绝并归零；不刷新超时 | `subject2_path_replay` |
| 任一点 frame 不是空或 `map` | 立即拒绝并归零 | `subject2_path_wrong_pose_frame` |
| 任一点 `x/y` 为 NaN 或 Inf | 立即拒绝并归零 | `subject2_path_nonfinite` |
| 路径停止刷新 | 最后一次有效接收 5 秒后归零 | `subject2_path_timeout` |
| 同几何、新时间戳 | 刷新超时，不重置进度 | 集成观察目标点 |
| frame、点数或任一点 `x/y` 改变 | 接受新路径并重置进度 | 集成发布新几何 |
| 仅 `z`、姿态、每点时间戳改变 | 接受刷新，不改变二维控制几何 | 集成检查；不建议依赖这些字段 |
| 点序反向、无序、自交或整体在车后 | 可能错误选点或因目标在车后归零 | 人工绘图并观察目标点 |
| 路径坐标与临时 `map=odom` 假设不一致 | 控制方向/位置错误，软件门禁不一定能识别 | 启动前人工对齐审核 |
| 适配器重启后时间戳回退 | 持续拒绝，直到超过历史值或控制器重启 | 重启注入并查日志 |
| `/localization/trusted_odom` 超过 0.30 s 未刷新 | 归零；保护器会锁存 stale 故障 | `subject2_odom_timeout` |
| 里程计单帧平移跳变 | `odom_valid=false`、保存最后可信值、归零 | `subject2_odom_jump` |
| 里程计时间戳为负、为零或纳秒越界 | `odom_valid=false`、锁存 `invalid_stamp`、保存最后可信值并归零 | 负秒：`subject2_odom_invalid_stamp`；字段边界：`test_ros_time` |
| `/localization/odom_valid=false` | 清除可信里程计和控制进度，归零 | 观察有效状态与命令 |
| 有效状态超过 0.50 s 未刷新 | 归零 | 停止保护节点后观察 |
| 故障后无合格 GPS，或 GPS 时间/frame/协方差/yaw 不可信 | 禁止导航；阶段超时进入 `ABORTED` | `subject2_recovery_no_gps` 及真实适配器输入校验 |
| 用 LIO `/lidar` NavSatFix、点云或 LIO odom 伪充 GPS | 禁止接入；这些不能提供独立全局锚点 | 接口审核，不是运行时自动识别 |
| LIO 重启服务失败/超时 | 进入 `ABORTED`，持续零速 | `subject2_recovery_restart_failed` |
| restart service 成功但新 GPS/odom 不稳定或无回显 | 不恢复行驶；超时后 `ABORTED` | 观察 `recovery_state`、`navigation_enabled`、`map_odom` |
| 新 `map→odom` 回显或最终可信 odom 与 GPS 不一致 | `ABORTED`，持续零速 | 恢复日志与 `/localization/map_odom` |
| `start_lio=false` 且外部系统未同时提供 `/localization/restart_lio` Trigger、`/localization/lio_generation` UInt32 和 `/localization/lio_process_alive` Bool | 无法完成自动恢复，最终 `ABORTED` | 检查服务类型以及两个 reliable/transient-local 状态话题；generation 须在重启前新鲜、重启后变化，alive 须为 true 且持续新鲜 |
| `map→odom` TF 缺失或查询失败 | 归零 | 停止 TF 发布者后观察 |
| 多个 `/cmd_vel` 发布者 | 测试失败，禁止连接执行机构 | `ros2 topic info -v /cmd_vel` |
| 下游不执行零命令/无独立看门狗 | 本仓库无法兜底，禁止实车 | 底盘团队独立测试 |

显式非法路径会清除当前路径，所以不是“继续沿上一条路径运行”。路径静默则最多沿最后有效路径运行 5 秒；这是当前实现差异，测试记录必须注明实际停车时间。

## 11. 实现边界与待验收项

已实现并可用合成 fixture 验证的软件链包括：里程计故障锁存和最后可信样本、GPS 位姿/协方差/稳定窗口门禁、受管 LIO 子进程组重启、重启后新 GPS 与新 odom 稳定验证、`map→odom` 更新和回显、guard 复位、最终一致性门禁，以及任一失败期间持续零速。

仍未实现或未验收的是：

- 真实 GPS 原始接口到 `/localization/gps_pose` 和 `/localization/gps_valid` 的生产适配器；
- 合作方真实路径接口到 `/subject2/path` 的生产适配器；
- 真实 GPS datum/轴向/yaw/协方差/天线外参和质量阈值验收；
- 真实 Horizon LIO 完整进程组在 RDK 上的重启、启动时延、新原点和超时参数验收；
- 实车制动、独立看门狗、低速行驶和故障恢复试验。

RDK 本轮离线，未访问也未测试。因此只能记录本机/容器与合成 fixture 证据，不得把它们写成 RDK、真实 GPS、真实 LIO 或实车通过。
